## Project structure

DiffeRT is a differentiable ray tracing toolbox for radio propagation, built on JAX. It is a mixed Python/Rust workspace with two packages:

- [differt/](differt/) — the main Python package (`differt`), installed in editable mode.
  - [differt/src/differt/](differt/src/differt/) — library source, one subpackage per topic: `geometry` (scenes, meshes, path tracers/launchers, ray/triangle geometry), `em` (electromagnetics: fields, materials, antennas, Fresnel/diffraction coefficients), `rt` (ray tracing re-exports), `scene` (scene I/O), `plotting` (backend-agnostic draw/dispatch utilities for matplotlib/plotly/vispy), `plugins` (optional integrations, e.g. `deepmimo`), `utils` (small generic helpers).
  - [differt/tests/](differt/tests/) — pytest suite, mirroring the source layout (`tests/geometry/`, `tests/em/`, etc.), plus `tests/benchmarks/`.
  - Private modules/functions are prefixed with `_` (e.g. `_solvers.py`, `_warp_utils.py`) and are not part of the public API; only names re-exported from a subpackage's `__init__.py` are public.
- [differt-core/](differt-core/) — a Rust extension module (`differt_core`), built with maturin/PyO3, exposing performance-critical graph/geometry primitives to Python.
  - `differt-core/src/` — Rust source; `differt-core/python/differt_core/` — the Python-facing package (type stubs, thin wrappers); `differt-core/tests/` — Python tests for the compiled extension; `differt-core/benches/` — Rust (Criterion) benchmarks.
- [docs/](docs/) — Sphinx documentation (MyST + autodoc/autosummary).
  - [docs/source/reference/](docs/source/reference/) — one hand-written `.rst` file per module (e.g. `differt.geometry.rst`) containing `.. autosummary::` blocks that list every public name, grouped under `.. rubric::` headings. `_autosummary/` is auto-generated by Sphinx — never edit it by hand.
  - [docs/source/notebooks/](docs/source/notebooks/) — tutorial notebooks (stripped of output on commit, except where `--keep-output` applies).
- [CHANGELOG.md](CHANGELOG.md) — Keep a Changelog-style, semver-ish changelog (see below).
- Uses `uv` for Python dependency/workspace management (`pyproject.toml`, `uv.lock`) and `just` as the task runner (`justfile`).

## Tools to use for development

Run everything from the repository root unless noted. Prefer the `just` recipes over calling the underlying tools directly — run `just --list` or `just docs/` to discover more.

- **Install/sync deps**: `uv sync` (or `just install`). Use `just install-profiling` for profiling GPU operations.
- **Rebuild the Rust extension** after touching `differt-core`: `uv sync --reinstall-package differt-core`, or install the auto-rebuild hook once with `just hook-install`.
- **Lint/format everything** (ruff, ty, cargo fmt/clippy, TOML/YAML formatting, notebook stripping, bibtex formatting, codespell, etc., via `prek`, this repo's pre-commit-hooks runner): `just lint` (alias `just fmt`). Run this before considering any change done.
- **Type-check**: covered by `just lint` (`ty`), but can be run standalone with `uv run ty check`.
- **Test Python**: `just test-python` (pytest). Test Rust: `just test-rust` (cargo test). Both: `just test`.
- **Benchmark**: `just bench-python` / `just bench-rust` / `just bench`.
- **Build docs**: `just docs/build` (see `just docs/` for other doc recipes); open `docs/build/html/index.html` to review.
- **Build the package**: `just build` (`uv build`).
- Do not invoke `pip`, `poetry`, `cargo add`, etc. directly for dependency changes — edit `pyproject.toml`/`Cargo.toml` and re-run `uv sync` / `cargo check` so lockfiles stay in sync.

## Checklist before finishing any code change

1. **Type annotations**: annotate the signature of every function/method you add or touch — public or private. For JAX arrays, always use jaxtyping shape/dtype-typed annotations (`Float[Array, "m 3"]`, `Int[Array, "*batch order"]`, `Complex[Array, "*batch 2 2"]`, a leading-space form like `Float[Array, " *batch"]` for a bare-batch scalar, etc.) from `jaxtyping` — **never** plain `jax.Array` or unannotated arrays, even in tests or throwaway helpers. Use `*batch`/`*#batch` conventions consistent with the surrounding code: the latter is only used for inputs sharing batch dimensions.
2. **Docstrings**: Google-style (`ruff`'s `pydocstyle` convention is `"google"`), required on every public function/method/class. Use Sphinx cross-reference roles instead of plain names/backticks: `:class:`, `:func:`, `:meth:`, `:attr:`, `:mod:`, with `~` to show only the last path component (e.g. ``:class:`~differt.geometry.Mesh` ``). For class methods or attributes, it is preferred to include the class name too, so use `` :meth:ClassName.method_name<differt.full_path_to.ClassName.method_name>``. Document `Args:`, `Returns:`, and `Raises:` sections when applicable. Private helpers should still get at least a one-line summary docstring. Each sentence should end with a period. When possible, add minimal code examples directly in the docstring.
3. **Public API docs**: if you add, rename, or remove a public class/function/method, update the matching `.. autosummary::` list in `docs/source/reference/differt.<module>.rst` (add it under the most fitting `.. rubric::` section, creating a new one only if none fits). Do not hand-edit anything under `docs/source/reference/_autosummary/` — it's generated.
4. **Deprecated code**: verify how deprecated members are currently modeled in the target module (see the `Deprecated classes` rubric in `differt.geometry.rst`) before renaming/removing a public name — old names are usually kept as deprecated aliases for a release or two.
5. **Changelog**: add an entry to the `## [Unreleased]` section of `CHANGELOG.md`, under `### Added` / `### Changed` / `### Fixed` / `### Removed` / `### Deprecated` as fitting (create the subsection if it doesn't exist yet, in that order, including its custom HTML anchor `(changelog-unreleased-<SUBSECTION_NAME>)=`). Subsection names are alphabetically ordered. Append new entries at the **end** of their subsection — entries are ordered from earliest-added to most-recently-added within a release, not the reverse. Use Sphinx cross-reference roles for any API name you mention (e.g. `` {class}`Mesh<differt.geometry.Mesh>` ``, `` {meth}`Scene.trace_paths()<differt.geometry.Scene.trace_paths>` ``). Prefix breaking changes with `**Breaking change**: `. End every entry with an attribution of the form `(by <gh-user:GITHUB_USERNAME>, in <gh-pr:PR_NUMBER>)` — use the actual contributor's GitHub username and the real PR number; if you don't know the PR number yet, leave a clearly marked placeholder (e.g. `<gh-pr:TODO>`) and flag it rather than inventing one.
6. **Tests**: add/update tests under `differt/tests/<module>/` (or `differt-core/tests/` for Rust-backed code) mirroring the source layout. Use one `test_<name>` function per free function tested, and one `Test<ClassName>` class (grouping one `test_<method>`-style method per behavior) for classes and their methods — follow the existing pattern in files like `differt/tests/geometry/test_solvers.py`. Reuse fixtures from `conftest.py` (`key`, `rng`, etc.) rather than constructing your own RNG/seed handling.
7. **Ruff/ty clean**: code must pass `just lint` with no new suppressions; this repo lints with `select = ["ALL"]` plus a curated ignore list in `pyproject.toml` — don't add new per-line `# noqa`/ignore comments to work around a rule instead of fixing the issue, and don't widen `[tool.ruff.lint.extend-ignore]` or `per-file-ignores` without a good reason.
8. **No stray notebooks/artifacts**: don't leave scratch scripts or notebooks (e.g. throwaway `Untitled.ipynb`-style files) checked into the repo; put exploratory work outside the tree or clean it up before finishing.
